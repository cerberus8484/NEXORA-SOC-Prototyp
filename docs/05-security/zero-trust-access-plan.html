Zero-Trust-Access-Plan

Identitaetszentrierter Zugang statt pauschalem Netz-Zutritt fuer Nexora, Operator-Zugriffe und spaetere Node-nahe Funktionen.

Der Plan ist bewusst produktneutral. `Twingate` oder `Tailscale` sind moegliche Vergleichskandidaten, aber keine Vorfestlegung.

01 Ziel

Privilegierter Zugang soll nicht aus LAN-/VPN-Naehe abgeleitet werden, sondern aus Identitaet, Kontext, expliziter Policy und Audit.

  1. App Access
  2. Operator Access
  3. Managed Node Access

02 Bereits vorhandene Bausteine

  • Cookie-only-Session + CSRF
  • Rollen und serverseitige Role-Gates
  • MFA/TOTP
  • OIDC-SSO
  • WebAuthn/Passkey
  • Audit-Log / Audit-Export
  • Control-Plane mit No-Apply-Modell

03 Sicherheitsziele

  • Kein privilegierter Zugang nur wegen Netzlage
  • MFA / Step-up fuer privilegierte Pfade
  • Kurze, widerrufbare Sessions
  • Ressourcenfreigabe pro Ziel statt Subnetzfreigabe
  • Zentrale Auditierbarkeit
  • Expliziter Break-Glass-Pfad
Nicht-Ziel dieses Tracks ist ein freier Remote-Exec-Kanal ueber die Nexora-Control-Plane.

05 Architekturziel

  • Ebene A - App Access: OIDC, MFA/Passkey, Re-Auth fuer High-Risk-Aktionen.
  • Ebene B - Operator Access: brokered access statt flat network reachability.
  • Ebene C - Managed Node Access: weiterhin keine freie Remote-Ausfuehrung.

06 Bewertungsrahmen

Ein Kandidat ist nur geeignet, wenn er OIDC/MFA sauber integrieren kann, Audit liefert, Windows- und Linux-Adminpfade praktikabel abdeckt und keine breite Netzfreigabe als Default erfordert.

07 Arbeitsablauf

  1. Management-Zielsysteme und Direktpfade inventarisieren
  2. Zugriffsklassen und Step-up-Matrix definieren
  3. 2-3 Zieloptionen gegen den Kriterienkatalog vergleichen
  4. Danach einen Implementierungs-ADR fuer die gewaehlte Loesung schreiben

08 Offene Entscheidungen

  • Welche Infrastrukturpfade muessen wirklich remote erreichbar sein?
  • Wie wird Break-Glass dokumentiert und technisch abgesichert?
  • Welche alten Direktpfade werden spaeter bewusst abgeschaltet?
