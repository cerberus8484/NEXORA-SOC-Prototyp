Hunt Response Console

Sicherer Weg von read-only Diagnosen zu genehmigten Response-Aktionen mit Audit-Trail.

Reale Endpoint-Wirkung bleibt ohne Agent aus. Optional kann HUNT_RESPONSE_AUTO_EXECUTE_MOCK=true genehmigte Containment-Aktionen fuer Demo- und Testzwecke als Mock bis completed durchlaufen lassen.

01 Zielbild

  1. Read-only Diagnose-Befehle gegen einen Host laufen lassen.
  2. Bei Verdacht einen Host isolieren, aber nur mit Genehmigung.
  3. Auf dem isolierten Host privilegiert arbeiten, ebenfalls nur mit Genehmigung.
Kernprinzip: Anfrage -> menschliche Genehmigung -> Ausfuehrung -> Audit.

03 Capabilities

canRunSafeCommand
canRequestPrivilegedCommand
canRequestHostIsolation
canApproveResponseAction
canExecuteResponseAction
canReleaseHostIsolation
  • Vier-Augen-Prinzip: requestedBy !== approvedBy.
  • Serverseitige Pruefung, nie nur im Frontend.
  • Rollen-Mapping zentral, spaeter pro Nutzer uebersteuerbar.

04 Datenmodell

ResponseAction
  kind: safe_command | privileged_command | isolate_host | release_isolation
  status: requested | approved | rejected | executing | completed | failed | expired
  riskTier: read_only | privileged | containment

Ohne Agent endet Stufe 2 bei approved mit Hinweis pending agent. Mit HUNT_RESPONSE_AUTO_EXECUTE_MOCK=true duerfen nur isolate_host und release_isolation als Mock ueber executing -> completed laufen. privileged_command bleibt genehmigt, aber nicht ausgefuehrt.

05 API

POST /v1/hunts/:id/response-actions
GET  /v1/hunts/:id/response-actions
POST /v1/response-actions/:id/approve
POST /v1/response-actions/:id/reject

Alle schreibenden Endpunkte erzeugen Audit-Eintraege mit Actor, Aktion, Ziel und Capability.

06 Agent-Vertrag

  • Allowlist auch am Agent, keine generische Shell-Weiterleitung.
  • Pull-Modell statt offenem Inbound-Port.
  • Signierte Commands, Agent verifiziert.
  • Isolation bleibt reversibel via release-isolation.

07 Threat Model

Command-InjectionServer-Allowlist, kein Shell-Passthrough

08 Audit

RESPONSE_REQUESTED, RESPONSE_APPROVED, RESPONSE_REJECTED, RESPONSE_EXECUTED, HOST_ISOLATED und HOST_ISOLATION_RELEASED werden inklusive Kontext protokolliert.

09 Umsetzung

  1. Safe-Command-Console
  2. Capability-Layer
  3. Approval-Gate fuer Response-Actions, optionaler Mock fuer Containment
  4. Realer Agent mit signierter Command-Queue

10 Offene Entscheidungen

  • Capability-Speicherung: statische Rollen-Map oder pro Nutzer in DB.
  • Agent-Technologie und Sicherheitsabnahme.
  • Eskalationspfad fuer ausstehende Freigaben.
  • Isolation nur Host-Firewall oder auch Netzwerk-Ebene.
