Network as Code

Vorkonfigurierte Open-Source-Systeme — Firewalls, SIEMs, IDS-Sensoren, Honeypots — aus Nexora heraus als VM auf einem Virtualisierer (Proxmox / ESXi) deployen. Deklarativ parametrisiert, modular, gegated und auditiert.

Die Deploy-Spec ist der Code: versioniert, validiert, wiederholbar — Plan → Approve → Apply wie in jeder IaC-Pipeline.

01 Was es ist

Das Deployment Center bringt das Prinzip von Infrastructure as Code in den SOC-Stack: statt eine Appliance von Hand auf dem Virtualisierer zu installieren und zu konfigurieren, beschreibt man sie deklarativ — welches System, welche Ressourcen, welche Netzwerk-Vorgaben (statische IP, VLAN, DNS) — und das System provisioniert sie reproduzierbar.

Abgrenzung zum bestehenden Provisioning in Nexora: das ist Agent-Enrollment (Token, Heartbeat) und zieht keine VMs hoch. Network as Code ist eine neue Fähigkeitsschicht — sie wiederverwendet aber dieselben Muster (Registry, Apply-Kanal, Audit, RBAC).

02 Prinzipien

Deklarativ

Du beschreibst den Zielzustand (Spec), nicht die Schritte. Das System leitet den Plan ab.

Modular

System-Module × Hypervisor-Connectoren. Neues System oder Virtualisierer = ein Modul nach Vertrag.

Parametrisiert

Vorgaben pro Deploy: IP, CIDR, Gateway, VLAN, DNS, Ressourcen, vendor-spezifisches.

Wiederholbar

Gleiche Spec → gleiches Ergebnis. Idempotent über Spec-Hash, kein Doppel-Deploy.

Gegated

Plan → Vier-Augen-Freigabe → Apply. ENV-Gate DEPLOY_ENABLED, default aus.

Auditiert

Jeder Schritt (clone, config, start, destroy) append-only protokolliert. Rollback bei Fehler.

04 Die Deploy-Spec (der Code)

Die Spec ist das deklarative Artefakt — versionierbar, reviewbar, wiederholbar:

# deploy-spec: OPNsense Firewall → Proxmox
module: opnsense
version: "24.7"
connector: proxmox-lab        # Hypervisor-Ziel (Connector-Instanz)
target:
  node: pve-01
  storage: local-lvm
  bridge: vmbr0
resources:
  cpu: 2
  ramMB: 2048
  diskGB: 20
params:
  hostname: fw-edge-01
  network:
    lan:
      ipMode: static
      ip: 10.0.10.1
      cidr: 24
      vlanTag: 10
    gateway: 10.0.10.254
    dns: [10.0.10.10, 1.1.1.1]
  adminPassword: ${secret:opnsense_admin}   # write-only — nie im Plan/Log
Die Spec wird gegen module.paramSchema validiert, bevor ein Plan entsteht. Secrets erscheinen weder im Plan noch im Audit noch im Return.

05 Parametrisierung

Jedes Modul deklariert seine Vorgaben. Ein gemeinsamer Netzwerk-Block gilt für alle Systeme, vendor-spezifisches kommt dazu.

07 Module & Connectoren (Erweiterbarkeit)

Die „jede Firewall der Welt"-Vision ist ein Vertrag, kein Sonderfall. Erweiterung kommt eins nach dem anderen — und ist selbst machbar:

System-Modul-Vertrag

  • identity — id, name, type (firewall/siem/ids/honeypot), vendor, version
  • source — Template-Referenz (klonen, bevorzugt) oder ISO + Erstinstallation
  • resourceDefaults — cpu, ramMB, diskGB
  • paramSchema — die konfigurierbaren Vorgaben (Typ, Validierung, Default, required)
  • configApplier — wie Vorgaben in die VM kommen (OPNsense: config-import · Linux: cloud-init/netplan)

Hypervisor-Connector-Vertrag

  • cloneFromTemplate · setResources · attachNetwork(bridge, vlanTag) · start · status · destroy · snapshot
  • Connector-Instanz = Host + API-Token (verschlüsselt), Ziel-Node, Storage, Bridge
Roadmap (eins nach dem anderen): 1. OPNsense → Proxmox · 2. ESXi-Connector · 3. Wazuh + Suricata-IDS-Sensor (cloud-init-Applier wiederverwendet) · danach Fortinet/Sophos/… als eigene Module. Jeweils mit Modul-Autoren-Doku.

08 Sicherheit

Network as Code schreibt echte Infrastruktur — entsprechend strikt:

  • Apply-Kanal: Draft → Vier-Augen-Approval → Plan/Dry-Run → Apply. Eigenes DEPLOY_ENABLED-ENV-Gate, default AUS (inert).
  • Reauth-Token vor Apply · RBAC admin · Rate-Limiting.
  • Hypervisor-Credentials verschlüsselt (SHA-256-gehasht wie NodeCredential), nie im Klartext/Return.
  • Vollständiges Audit jedes Schritts, append-only. Rollback (VM destroy) bei jedem Fehlerschritt.
  • Idempotenz über Spec-Hash — gleiche Spec erzeugt kein Doppel-Deploy.
  • API-Zugang zum Hypervisor nur über abgeschottetes Management-Netz, Token mit minimalen Rechten.

09 Vertikaler Schnitt: OPNsense → Proxmox

Der erste Beweis des Musters, in der Lab-Umgebung direkt greifbar (Proxmox-API vorhanden, OPNsense läuft dort schon als VM 117).

Definition of Done

Aus der UI: „OPNsense, LAN 10.0.10.1/24, VLAN 10, DNS 10.0.10.10, 2 vCPU / 2 GB" → Plan zeigt den Ablauf → Approve → Nexora klont das OPNsense-Golden-Template auf Proxmox, setzt Ressourcen + Netz/VLAN, startet, importiert die config.xml → OPNsense läuft mit genau dieser Vorgabe; alles auditiert; Fehler → Rollback.

Operator-Voraussetzung   Ein gepflegtes OPNsense-Golden-Template auf Proxmox + Proxmox-API-Token + existierende VLAN-Bridge. Das ist die Basis, von der geklont wird.
