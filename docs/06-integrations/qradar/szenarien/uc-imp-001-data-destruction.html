UC-IMP-001 — Data Destruction

Überwachung auffälliger Datenlöschung: Sabotage (System unbrauchbar machen), Anti-Forensik (Spuren verwischen) und Ransomware-Vorbereitung (Backups/Snapshots löschen). Quelle: GMK uc_013_imp_data_destruction.

MITRE: T1485 Data Destruction Taktik: Impact GMK-ID: uc_013 Quelle: Linux auditd (unlink/unlinkat) / Wazuh

1 · Hintergrund der Technik (T1485)

Wenn ein Angreifer im System ist, geht es in dieser Phase um echten Schaden bzw. das Verhindern der Wiederherstellung:

  • Sabotage: System unbrauchbar machen (Löschen von Konfigurationsdateien oder Datenbanken).
  • Anti-Forensik: Logs löschen (/var/log/), damit das SOC nicht mehr nachvollziehen kann, was passiert ist.
  • Ransomware-Vorbereitung: vor der Verschlüsselung Backups/Snapshots löschen, um den Zahlungsdruck zu erhöhen.

2 · Wann ist Löschen verdächtig?

Auf Linux werden ständig Dateien gelöscht (temp, Log-Rotation). Verdächtig wird es durch den Kontext:

MerkmalHarmlosVerdächtig
Mengeeinzelne Dateien / geplante Logstausende Dateien in Sekunden
Werkzeugrm, logrotateshred, wipe (sicheres Überschreiben)
Pfad/tmp, /var/cache/var/log, /etc, Backup-Mounts
BenutzerSystem-Dienste (root, logrotate, snapper)normaler User / Dienst-Account

4 · Voraussetzungen

  • Log-Quelle: auditd mit Watch auf Lösch-Syscalls (unlink, unlinkat, rmdir, rename) + execve für Wipe-Tools; an QRadar via Wazuh/Syslog.
  • Custom Event Properties: Command / exe syscall File Path Audit User (auid) Process Name
  • Reference Sets: RS:Logging-Maint-Procs (logrotate, systemd, snapper, rsyslogd) RS:Service-Accounts-Linux RS:Critical-Paths (Map: Pfad→Schwelle)

5 · Regeln A–C

Regel A — Einsatz von Anti-Forensik-Tools („Wiping")

Aufwand: Teil von Basis (s. Fazit)Empfehlung: Basis

Beobachtung: Ausführung von Programmen, die Dateien sicher überschreiben statt nur löschen. Warum: ein normaler Admin nutzt rm; ein Angreifer nutzt shred, damit Datenrettung unmöglich wird. Auf einem produktiven SLES-Server haben diese Tools im Alltag nichts zu suchen.

Apply UC-IMP-001-A Anti-Forensic Wiping on events detected by the Local system
and when Command/exe (custom) matches the regex (?i)/(shred|wipe|srm|scrub)$
Hohe Fidelity: nahezu kein FP auf Produktivservern. Response: Offense, Index by Host · Severity 8.

Regel B — Massenlöschung von Dateien (Ransomware-Indikator)

Aufwand: Teil von Basis (Baseline-intensiv)Empfehlung: Basis

Beobachtung: extrem hohe Anzahl Lösch-Operationen in kurzem Zeitfenster. Warum: Ransomware/Saboteur löscht tausende Dateien in Sekunden — eine klare Anomalie.

Apply UC-IMP-001-B Mass File Deletion on events detected by the Local system
and when syscall (custom) is one of the following unlink, unlinkat, rmdir
and when the Audit User (auid) is NOT contained in RS:Logging-Maint-Procs
and when at least 500 events are seen with the same Username and same Source Host in 10 seconds
Schwelle ist nicht „aus dem Bauch". Der Wert 500/10 s ist ein Startpunkt — die echte Schwelle ergibt sich aus der Baseline (siehe Abschnitt 6). FP: snapper-Cleanup, große Build-/Cache-Löschungen → Wartungsprozesse whitelisten.

Regel C — Manipulation / Löschung der System-Logs

Aufwand: 5–10 h (Synergie mit T1070)Empfehlung: Erweitert

Beobachtung: Löschbefehle in kritischen Log-Verzeichnissen, die nicht vom System stammen. Warum: ohne Logs ist das SOC blind — Angreifer leeren/löschen fast immer audit.log oder messages, um Spuren zu vertuschen.

Apply UC-IMP-001-C System Log Tampering on events detected by the Local system
and when syscall (custom) is one of the following unlink, unlinkat, truncate, rename
and when File Path (custom) matches the regex ^/var/log/
and when the Process Name is NOT contained in RS:Logging-Maint-Procs
Synergie mit T1070 Clear Linux Logs: die technischen auditd-Watch-Rules aus dem bestehenden T1070-Use-Case lassen sich mitnutzen — daher der geringe Aufwand. Reizvoll als Regelverknüpfung (Chaining): Massenlöschung (B) + Log-Löschung (C) → erhöhte Severity.

6 · Baseline & pfadabhängige Logik

Der größte Aufwand steckt nicht in der Regel selbst, sondern darin zu wissen, was „normal" ist:

  • Baseline: unlink/unlinkat-Events über 30 Tage auswerten (je System, je User/Service-Account, je Pfad). Schwelle = z. B. Baseline × Faktor 2–3 → Alarm.
  • Pfadabhängig: in /tmp sind hunderte Löschungen normal; in /etc oder /boot sind 5 Löschungen schon verdächtig. Umsetzbar über die Map RS:Critical-Paths (Pfad → niedrige Schwelle) und separate strenge Regeln für /etc, /boot, Backup-Mounts.
  • Langfrist-Alternative: UEBA-Inbetriebnahme abwarten — dann übernimmt das Verhaltensmodell die Baseline.

7 · Aufwand & Empfehlung (GMK-Fazit)

Basis-Absicherung (A, B): destruktive Aktivität durch Ransomware/Sabotage (Massenlöschung + Wipe-Tools). Aufwand ca. 70–90 h — enthält die aufwendige Baseline-Ermittlung, Whitelisting von Systemdiensten (snapper, logrotate) und pfadabhängige Priorisierung (z. B. Alarm bei nur 1 Löschung in /boot).
Erweiterte Detektion (C): gezielter Schutz der Log-Integrität (Synergie mit T1070). Aufwand ca. 5–10 h, da technische Audit-Rules aus T1070 mitgenutzt werden; Aufwand fließt v. a. in Korrelation/Alarm-Logik in QRadar.

9 · Analyst-Handlung

  • Prozess + Konto (auid) + betroffene Pfade sichern; war shred/wipe beteiligt?
  • Bei Log-Löschung: parallele Aktivität in anderen UCs prüfen — der Angreifer verwischt gerade Spuren.
  • Snapshots/Backups auf Vollständigkeit prüfen (Ransomware-Vorbereitung?). Übergang zu uc_014 beobachten.
  • Bei bestätigter Zerstörung: Host isolieren, aus sauberem Backup wiederherstellen.
