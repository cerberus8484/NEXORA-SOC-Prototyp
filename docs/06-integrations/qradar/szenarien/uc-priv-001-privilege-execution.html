UC-PRIV-001 — Privilege / User Execution

Überwachung der Ausführung von Befehlen zur Umgehung von Berechtigungen auf Linux-Systemen: missbräuchliche sudo-Nutzung, Manipulation von SUID-Binaries und Ausbeutung von pkexec (PolicyKit). Zielumgebung: SLES-Server im vCenter. Quelle: GMK uc_010_priv_user_execution.

MITRE: T1548 Abuse Elevation Control Mechanism Taktik: Privilege Escalation GMK-ID: uc_010 Quelle: Linux auditd / Wazuh / syslog

1 · Hintergrund der Technik (T1548)

Angreifer starten fast immer als „Niemand" — z. B. über einen gehackten Webserver-User wie www-data. In diesem Zustand können sie keine Passwörter auslesen, keine Sicherheitssoftware stoppen und keine Daten anderer User einsehen. T1548 beschreibt den Versuch, diese Barriere zu durchbrechen und an Root-Rechte zu gelangen.

Hoch-kritisch: Erfolgreiche Rechteausweitung auf Root = vollständige Kontrolle über das System; Ausgangspunkt für Persistenz, Datenzerstörung (uc_013) und Verschlüsselung (uc_014).

2 · Ist jedes sudo verdächtig?

Nein. Admins führen täglich dutzende sudo-Befehle aus (Updates, Konfigurationen). Verdächtig wird es durch den Kontext:

MerkmalHarmlos (legitim)Verdächtig (Angriff)
Benutzerbekannter Admin-UserDienst-Account (apache, tomcat, www-data)
Befehlzypper update, systemctl restartwhoami, cat /etc/shadow, chmod +s /usr/bin/python
Häufigkeitgelegentlich während der Arbeitszeitmassenhafte Versuche in Sekunden (Brute Force)

4 · Voraussetzungen

  • Log-Quelle: SLES-Hosts senden auditd + Auth-Logs (/var/log/messages bzw. secure, sudo, PAM) an QRadar — direkt via Syslog-DSM oder über Wazuh.
  • Auditd-Regeln deployt (sonst keine Events für C/D): SUID-Bit-Setzen und pkexec-execve.
  • Custom Event Properties: Command / exe Audit User (auid) TTY syscall File Path audit key
  • Reference Sets: RS:Sudo-Admins (AlphaNumeric) RS:Service-Accounts-Linux (AlphaNumeric) RS:SUID-Maintenance-Hosts (IP)

5 · Regeln A–E

Jede Regel = eine eigene Event Rule (Rule Group Privilege Escalation). Blau = anklickbarer Wizard-Parameter.

Regel A — Sudo Brute Force Detection

Aufwand: 15–20 hEmpfehlung: BasisVoraussetzung: direkt umsetzbar (analog SSH-Login-Failure-UC)

Beobachtung: mehrfache authentication failure bei sudo (auth.log/secure). Warum: erkennt Passwort-Raten.

Apply UC-PRIV-001-A Sudo Brute Force on events detected by the Local system
and when Command/exe (custom) is one of the following /usr/bin/sudo
and when the event message matches the regex (?i)authentication failure|incorrect password
and when at least 5 events are seen with the same Username and same Source Host in 5 minutes
Response: Offense, Index by Username · Severity 6 · Limiter 1×/10 min. FP: User vertippt sich — Schwelle 5/5 min puffert das.

Regel B — Unerwartete Sudo-Nutzer („Service-Account"-Regel)

Aufwand: 25–30 hEmpfehlung: BasisVoraussetzung: vollständige Liste aller Admin- + berechtigten Service-Accounts

Beobachtung: jeder erfolgreiche sudo-Aufruf durch Nicht-Admins. Warum: www-data oder ein DB-User sollte niemals sudo nutzen.

Apply UC-PRIV-001-B Unexpected Sudo User on events detected by the Local system
and when the event message matches the regex (?i)sudo:.*COMMAND=  (erfolgreiche sudo-Ausführung)
and when the username is NOT contained in RS:Sudo-Admins
and when the username is NOT contained in RS:Service-Accounts-Linux
Steht und fällt mit der Whitelist. Bereitstellung einer gepflegten Liste personalisierter Admin-Accounts + berechtigter Service-Accounts (Monitoring/Backup) ist Pflicht. Onboarding-Prozess für RS:Sudo-Admins definieren, sonst FP bei neuen Admins.

Regel C — SUID-Binary Manipulation

Aufwand: 25–30 hEmpfehlung: BasisVoraussetzung: Anpassung auditd-Rules → direkt umsetzbar

Beobachtung: chmod +s / chown root auf ausführbare Dateien (auditd-Syscalls, die das SUID-Bit setzen). Warum: SUID lässt ein Programm immer mit Root-Rechten laufen — Angreifer bauen sich so eine Root-Bash als Hintertür.

# auditd-Regel (auf den Hosts): SUID-Setzen protokollieren
-a always,exit -F arch=b64 -S chmod,fchmod,fchmodat -F a1&04000 -k suid_change

Apply UC-PRIV-001-C SUID Manipulation on events detected by the Local system
and when audit key (custom) is one of the following suid_change
and when syscall (custom) is one of the following chmod, fchmod, fchmodat
and when the Audit User (auid) is NOT contained in RS:Service-Accounts-Linux
and when the source IP is NOT contained in RS:SUID-Maintenance-Hosts
FP: Paket-Updates (zypper/RPM-Postinstall) setzen SUID-Bits — Paketmanager-Kontext (auid = Service-Account / Wartungsfenster) whitelisten.

Regel D — PolicyKit / Polkit (pkexec) Ausbeutung (T1548.004)

Aufwand: ca. 30–40 hEmpfehlung: ErweitertVoraussetzung: Anpassung auditd-Rules → direkt umsetzbar

Beobachtung: Ausführung von /usr/bin/pkexec durch Nicht-Admins. Warum: pkexec ist das grafische Gegenstück zu sudo; bekannte Lücken (PwnKit) erlangen darüber ohne Passwort Root. Auf SLES-Servern im vCenter bedienen normale User selten grafische Oberflächen → pkexec durch Nicht-Admins ist extrem verdächtig.

Apply UC-PRIV-001-D pkexec Exploitation on events detected by the Local system
and when Command/exe (custom) is one of the following /usr/bin/pkexec
and when the username is NOT contained in RS:Sudo-Admins
Verhalten statt Signatur: Die Regel zielt nicht auf eine spezifische CVE, sondern darauf, dass ein normaler User überhaupt pkexec nutzt. Auch eine künftige, noch unbekannte Polkit-Lücke schlägt damit an. Quelle: SUSE KB CVE-2021-4034. Response: Offense, Severity 8.

Regel E — Sudo-Aufruf ohne Terminal (TTY) (T1548.003)

Aufwand: ca. 30–40 hEmpfehlung: ErweitertVoraussetzung: Cron-/Ansible-Whitelist + erweiterte Linux-DSM-Anpassung

Beobachtung: sudo-Befehle ohne zugeordnetes Terminal (TTY=none / ?). Warum: Menschen haben beim sudo immer ein Terminal. Automatisierte Exploit-Skripte und Reverse-Shells haben keines — ein sudo ohne TTY deutet stark auf eingeschleuste Hintergrund-Rechteausweitung hin.

Apply UC-PRIV-001-E Sudo Without TTY on events detected by the Local system
and when the event message matches the regex (?i)sudo:.*COMMAND=
and when TTY (custom) is one of the following unknown, none
and when the username is NOT contained in RS:Service-Accounts-Linux
FP-Achtung: Cron-Jobs, Ansible, CI/CD nutzen sudo ohne TTY völlig legitim. Darum „Erweitert" — die berechtigten Automatisierungskonten müssen sauber in RS:Service-Accounts-Linux stehen (in der Testphase im SIEM auslesbar), sonst hohe FP-Rate.

6 · Aufwand & Empfehlung (GMK-Fazit)

Basis-Absicherung (A, B, C): deckt die kritischsten Vektoren ab (Brute Force, unbefugtes Sudo, SUID-Hintertüren) — ~80 % der gängigen Privilege-Escalation-Szenarien. Aufwand ca. 60–80 h.
Erweiterte Detektion (D, E): Schutz gegen Polkit-Exploits & automatisierte Reverse-Shells, inkl. moderner Zero-Days. Aufwand je Regel ca. 30–40 h.

8 · Analyst-Handlung

  • Betroffener Host + Konto (auid) + ausgeführter Befehl (COMMAND=) sichern.
  • Bei SUID: welches Binary wurde manipuliert? (GTFOBins-Kandidat?) → entfernen, Integrität prüfen.
  • Bei pkexec/PwnKit: Polkit-Patchstand prüfen, Host als kompromittiert behandeln.
  • Folge-Aktivität korrelieren (neue Konten, Cron-Persistenz, ausgehende Verbindungen, Übergang zu uc_013 / uc_014).
