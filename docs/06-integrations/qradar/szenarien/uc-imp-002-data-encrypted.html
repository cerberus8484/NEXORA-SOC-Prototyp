UC-IMP-002 — Data Encrypted for Impact

Überwachung der Verschlüsselung vieler Daten in kurzer Zeit. Ein Prozess liest massenhaft Dateien, verschlüsselt sie im Speicher und schreibt sie als neue, unlesbare Dateien zurück (oft mit neuer Endung wie .crypt). Quelle: GMK uc_014_imp_data_encrypted.

MITRE: T1486 Data Encrypted for Impact Taktik: Impact GMK-ID: uc_014 Quelle: Linux auditd (openat/write/rename/unlink) / Wazuh FIM

1 · Hintergrund der Technik (T1486)

Sobald der Angreifer administrative Rechte hat (siehe uc_010) und Backups manipuliert hat (siehe uc_013), werden Daten verschlüsselt, um sie unbrauchbar zu machen — Ziel ist die Erpressung von Lösegeld durch Entzug der Datenverfügbarkeit.

2 · Wann ist Verschlüsselung verdächtig?

Auf Linux-Servern gibt es legitime Verschlüsselung (Backups, Datenbanken, TLS). Verdächtig wird es durch Muster und Kontext:

MerkmalHarmlosVerdächtig
Mustergezielte Verschlüsselung einzelner ArchiveRead → Write → Delete auf tausenden Dateien
Mengeeinzelne Dateien / geplante Jobstausende Dateien in kurzer Zeit
Userdedizierter Backup-/System-Accountnormaler User / kompromittierter Service-Account
PfadBackup-VerzeichnisseHome-Verzeichnisse, Shares, /etc
Systemlastkurze, bekannte Lastspitzenmassive, langanhaltende CPU-Last
Dateiendungenunverändertneue/ungewöhnliche Endungen (.enc, .locked)

4 · Voraussetzungen

  • Custom Event Properties: syscall File Path Process Name Audit User (auid)
  • Reference Sets: RS:Backup-Crypto-Procs (borg, restic, gpg, tar, gzip, mysqldump) RS:Ransomware-Extensions (Set) RS:Honeyfile-Paths (Set)

5 · Regeln A–F

Regel A — Ransomware-Verhaltensmuster (Read-Write-Delete)

Aufwand: hochEmpfehlung: Basis (Kernregel)

Beobachtung: schnelle Abfolge Öffnen-zum-Lesen → neue Datei erstellen → alte Datei löschen, in einem Verzeichnis. Warum: Ransomware ersetzt das Original durch die verschlüsselte Version — dieser „Austausch-Rhythmus" ist das sicherste Merkmal.

Apply UC-IMP-002-A Ransomware Read-Write-Delete
and when a sequence of openat → write/create → unlink occurs
        for the same Process on hundreds of files in 60 seconds
Ehrlicher Status: Sehr präzise, aber technisch schwer umsetzbar — die Event-Korrelation ist anspruchsvoll (Events kommen verzögert, in falscher Reihenfolge). Erfordert DSM-Anpassungen, ggf. Custom Action Scripts (zeitintensiv). In der Praxis oft über Regel A2 als pragmatischen Ersatz abgebildet.

Regel A2 — Vereinfachte Massenänderung (Fallback / Alternative zu A)

Aufwand: mittel (Baseline-intensiv)Empfehlung: Basis (Alternative zu A)

Beobachtung: hohe Anzahl Schreib-/Umbenennungs-Operationen. Warum: einfacher umzusetzende Alternative zur Sequenz-Erkennung.

Apply UC-IMP-002-A2 Mass File Modification on events detected by the Local system
and when syscall (custom) is one of the following write, rename, openat(O_CREAT)
and when the Process Name is NOT contained in RS:Backup-Crypto-Procs
and when at least 1000 events are seen with the same Process in 60 seconds
Baseline nötig: Schwelle je System über einen Zeitraum ermitteln (was ist „normal"?). 1000/60 s ist Startwert.

Regel B — Bekannte Ransomware-Dateiendungen

Aufwand: gering („Low-Hanging-Fruit")Empfehlung: Basis

Beobachtung: Erstellung von Dateien mit typischen Ransomware-Endungen. Warum: viele Skripte hängen eine feste Endung an.

Apply UC-IMP-002-B Ransomware Extensions on events detected by the Local system
and when syscall (custom) is one of the following rename, openat(O_CREAT)
and when File Path (custom) matches the regex
        (?i)\.(locked|crypt|crypted|enc|locky|wannacry|wcry|crypt7|cerber)$
Pflege über Reference Set: Endungen in RS:Ransomware-Extensions halten, statt Regex hartzukodieren → leicht erweiterbar. Response: Offense, Severity 9.

Regel C — Überhöhte CPU-Last durch unbekannte Prozesse

Aufwand: —Empfehlung: Erweitert — derzeit NICHT umsetzbar

Beobachtung: ein Prozess verbraucht über längere Zeit ungewöhnlich viel CPU (Kryptographie ist rechenintensiv).

Out of scope (ehrlich): Diese Regel erfordert die Integration von System-Monitoring-/Performance-Daten ins SIEM. Laut GMK-Vorgabe gilt: „Wir machen kein System-Monitoring." Regel C ist damit an die zukünftige Bereitstellung von Performance-Metriken gebunden und derzeit nicht baubar. Hier dokumentiert, damit die Lücke bewusst bleibt — nicht als aktiver Use Case.

Regel D — Massenhafte Umbenennung von Dateien

Aufwand: mittel (Baseline)Empfehlung: Basis

Beobachtung: viele rename-Events in kurzer Zeit. Warum: viele Ransomware-Varianten ändern Dateinamen systematisch.

Apply UC-IMP-002-D Mass File Rename on events detected by the Local system
and when syscall (custom) is one of the following rename, renameat, renameat2
and when the Process Name is NOT contained in RS:Backup-Crypto-Procs
and when at least 500 events are seen with the same Process in 60 seconds
Baseline je System über einen Zeitraum auswerten, um die Schwelle robust zu setzen.

Regel E — Zugriff auf ungewöhnlich viele Verzeichnisse

Aufwand: Teil der Erweiterung (Streuungs-Logik)Empfehlung: Erweitert

Beobachtung: ein Prozess verteilt Dateioperationen über viele unterschiedliche Verzeichnisse und überschreitet sein übliches Arbeitsverzeichnis. Warum: normale Prozesse sind lokal begrenzt, Ransomware arbeitet systemweit.

Apply UC-IMP-002-E Directory Spread on events detected by the Local system
and when syscall (custom) is one of the following write, rename, unlink
and when at least 50 events are seen with the same Process
        and different Directory (File Path parent) in 60 seconds
Kern der Erweiterung: der Aufwand fließt primär in die Logik zur Verzeichnis-Streuung — systemweite von lokal begrenzten Dienst-Aktivitäten unterscheiden. Erkennt auch „getarnte"/langsame Verschlüsselung unterhalb der Massen-Schwellen.

Regel F — Honeyfile-Zugriffe ★

Aufwand: geringEmpfehlung: Basis (höchste Präzision)

Beobachtung: jeglicher Schreib-/Umbenennungs-/Löschzugriff auf speziell präparierte Honeyfile-Verzeichnisse. Warum: kein legitimer User und kein Systemdienst kennt diese versteckten Ordner. Ransomware scannt das Dateisystem alphabetisch ab und stolpert zwangsläufig darüber.

Apply UC-IMP-002-F Honeyfile Access on events detected by the Local system
and when syscall (custom) is one of the following write, rename, unlink, openat
and when File Path (custom) is contained in RS:Honeyfile-Paths
100 %-Indikator ohne Fehlalarme. Versteckte Ordner anlegen (z. B. .backup, früh im Alphabet einsortiert) und per auditd überwachen. Jede write-Operation darauf = Alarm. Voraussetzung: Honeyfiles auf den Hosts ausbringen + auditd-Watch + Pfade in RS:Honeyfile-Paths. Auch für uc_013 nutzbar.

6 · Aufwand & Empfehlung (GMK-Fazit)

Basis-Absicherung (A, A2, B, D, F): aktive Verschlüsselungsvorgänge (Read-Write-Delete-Muster, Massenänderungen, auffällige Endungen) + hochpräziser Honeyfile-UC. Aufwand ca. 110–130 h — enthält komplexe Korrelation (v. a. Sequenz für A), robuste Schwellwerte, Baseline-Ermittlung und umfangreiches Whitelisting (Backup-Software, DB, Komprimierungstools).
Erweiterte Detektion (E, [C]): anomales Prozessverhalten & getarnte/langsame Verschlüsselung. Aufwand ca. 30–40 h — primär die Verzeichnis-Streuungs-Logik (E). Regel C ist an künftige Performance-Metriken gebunden (kein System-Monitoring) und derzeit nicht enthalten.

8 · Analyst-Handlung

  • Sofort: verursachenden Prozess identifizieren und stoppen (Process Name / auid), Host isolieren — bei aktiver Verschlüsselung zählt jede Sekunde.
  • Umfang feststellen: betroffene Pfade/Verzeichnisse, Dateiendung, Startzeit.
  • Rückkette prüfen: vorher Rechteausweitung (uc_010) und Backup-/Snapshot-Löschung (uc_013)?
  • Wiederherstellung aus sauberem, offline gehaltenem Backup; Eintrittsvektor schließen.
