UC-CRED-002 — Kerberoasting

Ein authentifizierter Angreifer fordert Kerberos-Service-Tickets (TGS) für Konten mit einem Service Principal Name (SPN) an und crackt die enthaltenen Passwort-Hashes offline. Kein Eingriff auf dem Zielkonto nötig, kein Admin-Recht erforderlich — jedes Domänenkonto genügt. Darum ist Kerberoasting eine der häufigsten und gefährlichsten AD-Techniken.

MITRE: T1558.003 Taktik: Credential Access Confidence: 85–90 Status: DRAFT → zu validieren Quelle: Windows Security 4769 (DC)

1 · Szenario

Service-Konten in Active Directory (z. B. svc_sql, svc_iis) haben oft einen registrierten SPN, damit Kerberos für sie Service-Tickets ausstellen kann. Beim Anfordern eines TGS verschlüsselt der Domain Controller einen Teil des Tickets mit dem NTLM-Hash des Service-Konto-Passworts. Wer ein gültiges Domänenkonto besitzt, kann diese Tickets massenhaft anfordern und sie anschließend offline mit Hashcat/John brute-forcen — ohne dass am Service-Konto selbst etwas auffällt.

Warum so gefährlich: Service-Konten haben häufig (a) schwache, alte Passwörter, (b) keine MFA, (c) hohe Privilegien (lokaler Admin auf vielen Servern, manchmal Domänen-Admin). Ein gecracktes Service-Konto = oft direkter Weg zur Domänen-Übernahme.

2 · Angriffsablauf

  1. Domänenzugang: Angreifer hat ein beliebiges gültiges Domänenkonto (Phishing, geleakte Credentials, Standard-User).
  2. SPN-Enumeration: Auflisten aller Konten mit SPN per LDAP — GetUserSPNs.py, Rubeus kerberoast /stats, PowerView Get-NetUser -SPN. Erzeugt keine 4769-Events.
  3. TGS-Anforderung: Für jeden SPN wird ein Service-Ticket angefordert. Hier entstehen die 4769-Events — mit Encryption Type 0x17 (RC4), wenn der Angreifer RC4 erzwingt.
  4. Offline-Cracking: Die Ticket-Hashes ($krb5tgs$23$...) werden exportiert und mit Hashcat (Mode 13100) gecrackt — außerhalb des Netzes, unsichtbar.
  5. Verwertung: Mit dem geknackten Klartext-Passwort meldet sich der Angreifer als Service-Konto an → Lateral Movement / Privilege Escalation.
Erkennungs-Fenster: Sichtbar ist nur Schritt 3 (4769). Enumeration (2) und Cracking (4) sind unsichtbar. Deshalb zielt der Use Case auf das Muster der TGS-Anforderungen: viele verschiedene SPNs, RC4, von einer Workstation.

4 · Warum RC4 (0x17) der Schlüssel-Indikator ist

Der DC verschlüsselt das Service-Ticket mit dem stärksten Schlüssel, den das Konto unterstützt. RC4 leitet sich direkt vom NTLM-Hash ab und ist offline um Größenordnungen schneller crackbar als AES. Angreifer fordern darum gezielt RC4 an (Rubeus kerberoast /rc4opsec / Downgrade). Ein RC4-TGS für ein modernes Konto, das eigentlich AES kann, ist hochverdächtig.

Ticket Encryption TypeBedeutungRelevanz
0x17RC4-HMACKerberoasting-Indikator — schnell crackbar
0x18RC4-HMAC-EXPLegacy, ebenfalls verdächtig
0x12AES256-CTS-HMAC-SHA1Normalfall, schwer crackbar
0x11AES128-CTS-HMAC-SHA1Normalfall
0x1 / 0x3DES (CRC / MD5)Stark veraltet — sollte deaktiviert sein
Tuning-Hinweis: In modernen Domänen (AES erzwungen) ist jedes 0x17-TGS verdächtig — Schwelle niedriger setzen. In Alt-Umgebungen mit Legacy-RC4 muss die Schwelle höher und die Whitelist gepflegt sein, sonst Rauschen.

5 · Voraussetzungen

  • Log-Quelle: Alle Domain Controller senden EventID 4769 (Kerberos Service Ticket Operations) an QRadar. Audit-Policy „Audit Kerberos Service Ticket Operations" muss aktiv sein.
  • Custom Event Properties (per DSM-Editor extrahieren, dann im Log-Activity-Tab prüfen dass sie gefüllt sind):
    Ticket Encryption Type Service Name Account Name Client Address
  • Reference Set: RS:Kerberos-Service-Hosts (Type IP) — Hosts, die legitim viele Tickets anfordern (SQL-, Exchange-, App-Server).

6 · Erkennungslogik

6.1 — QRadar Rule Wizard (GUI)

Actions → New Event Rule · Rule Group Credential Access · Name UC-CRED-002 Kerberoasting. Blau = anklickbarer Parameter.

Apply UC-CRED-002 Kerberoasting on events detected by the Local system
and when the event QID is one of the following (Kerberos Service Ticket Requested / 4769)
and when Ticket Encryption Type (custom) is one of the following 0x17, 0x18
and when Service Name (custom) does NOT match the regex (?i)(krbtgt|\$$)
and when at least 10 events are seen with the same Source IP
        and different Service Name in 1 hour
and when the source IP is NOT contained in RS:Kerberos-Service-Hosts
Test-Name im Stack: when at least N events are seen with the same <property> and different <property> in <time> — das „different Service Name" ist entscheidend: es zählt unterschiedliche SPNs, nicht Wiederholungen.

6.2 — Referenz-AQL (zum Verständnis / Hunting)

SELECT sourceip, "Account Name",
       COUNT(DISTINCT "Service Name") AS distinct_spns,
       COUNT(*) AS ticket_count
FROM events
WHERE "Event ID" = '4769'
  AND "Ticket Encryption Type" = '0x17'
  AND "Service Name" NOT LIKE '%$'
  AND "Service Name" != 'krbtgt'
  AND sourceip NOT IN (SELECT ip FROM reference set 'RS:Kerberos-Service-Hosts')
GROUP BY sourceip, "Account Name"
HAVING distinct_spns >= 10
LAST 1 HOURS

11 · Analyst-Handlung & Evidence

Bei Offense zu sammeln:

  • Quell-Host (Source IP) + angemeldetes User-Konto (4769 „Account Name") → wer hat geroastet?
  • Liste der angefragten SPNs (Service Names) → welche Service-Konten sind gefährdet?
  • Zeitfenster + Ticket-Anzahl → Umfang.
  • Korrelation: vorher 4768 (TGT) vom selben Host? Danach Logon mit einem der Service-Konten?

Sofortmaßnahmen: Passwörter der betroffenen Service-Konten rotieren (lange, zufällige), AES erzwingen / RC4 deaktivieren, ggf. auf Group Managed Service Accounts (gMSA) umstellen. Quell-Host und User-Konto untersuchen.
