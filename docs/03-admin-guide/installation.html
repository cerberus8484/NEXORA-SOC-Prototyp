01 Überblick & Architektur

Nexora SOC ist eine selbst-gehostete SOC-Plattform (Incident-Tickets, Threat Hunting, KI-Triage-Agent, Live-Telemetrie). Sie besteht aus drei Kern-Containern und mehreren optionalen externen Diensten.

┌────────────────────────────────┌ Browser ─► 443 web (nginx + TLS) │ ├─ serviert React-SPA (frontend/dist) │ └─ /api ─► proxy ──► api:3000 │ │ │ api (Node/Express) ─► postgres └────────────────────────────────── │ (optional, nach außen) Ollama (LLM) ● Qdrant (RAG) ● Wazuh (API :55000 + Indexer :9200)
BausteinTechnikPflicht?
webnginx, serviert React-SPA, TLS, Reverse-Proxy /apiPflicht (Prod)
apiNode.js + Express, Repository-Pattern, Migrationen auto bei BootPflicht
postgresPostgreSQL 16 (Tickets, User, Audit, Hunts)Pflicht f. Persistenz
OllamaLokales LLM für KI-Agent (eigene LXC)Optional
QdrantVektor-DB für RAG-WissensbasisOptional
WazuhSIEM — Alerts (Webhook) + Indexer-Daten (Dashboard)Optional
Ohne Postgres läuft das Backend auf InMemory-Repositories — nichts überlebt einen Neustart (nur Tests/Dev). Schalter: DB_ENABLED. Ohne Ollama bleibt der KI-Agent auf dem stub-Provider (deterministisch, kein LLM). Schalter: AGENT_LLM_PROVIDER.

Architektur-Prinzipien (aus ROADMAP.md)

  • Repository-Pattern: InMemory für Tests/Dev, Postgres bei DB_ENABLED=true (per-Domain-Factory).
  • Migrationen automatisch bei Boot: server.js → bootstrap() ruft migrate() vor app.listen(). Idempotent (IF NOT EXISTS).
  • Fail-Fast: In Produktion bricht der Start ab, wenn Pflicht-Secrets fehlen (config/validateEnv.js).
  • Keine Integration ohne Adapter, kein externer Input ohne Validierung.

Postgres + API + Frontend in Containern. Quelle: docker-compose.dev.yml.

docker compose -f docker-compose.dev.yml logs -f api web
docker compose -f docker-compose.dev.yml down

Erster Start ist langsam (npm install in beiden Containern). Danach liegen die node_modules in Named Volumes — Start ist schnell.
Dev-Seed-Login (automatisch idempotent angelegt): admin@nexora.example / DevAdmin123!
Alle Dev-Secrets in docker-compose.dev.yml (JWT_SECRET=dev-only-…, DB_PASSWORD=devpassword) sind nur für lokale Entwicklung — niemals in Prod.

Variante B — Nativ ohne Docker (aus README.md)

# Backend

npm test

# Frontend (zweites Terminal)
cd frontend && npm install
npm run dev            # http://localhost:5173

# Admin im Dev-Modus via ENV bootstrappen

Mit Persistenz nativ: DB_ENABLED=true + DB-Verbindungsdaten setzen.

05 Datenbank & Migrationen

Mechanismus (db/pool.js + server.js)

  • bootstrap() ruft — nur bei DB_ENABLED=true — zuerst migrate(), dann ping(), vor app.listen().
  • migrate() liest alle *.sql aus backend/src/db/migrations/, sortiert alphabetisch (readdirSync().sort()), führt der Reihe nach aus.
  • Alle Migrationen sind idempotent (IF NOT EXISTS) — kein separates Framework, keine Versions-Tabelle.
Aktueller Stand: 28 Migrationen (001 … 028) — von 001_create_tickets über 017_ticket_number_seq, 021_agent_suggestion_analysis, 027_autonomy_policies bis 028_user_profile_fields.

Manuell migrieren (neue Migration ohne Neustart)

docker compose -f deploy/docker-compose.prod.yml --env-file deploy/.env.production \
  exec api node -e "require('./src/db/pool').migrate().then(() => process.exit(0))"
Wichtig: Neue Migrationsdateien so benennen, dass die alphabetische Sortierung der gewünschten Reihenfolge entspricht (führende Nullen, z.B. 029_…).

06 Produktions-Deployment

Kontext: Linux/Ubuntu-VM, im Lab Proxmox (ROADMAP P15). Die aktuelle Produktiv-Referenz liegt unter /opt/SOC-Orchestrator. Falls eine Umgebung historisch abweicht, vor jedem Eingriff zuerst pwd und git branch --show-current prüfen statt alte Pfade blind zu übernehmen.

6.1 Ersteinrichtung (deploy/README.md)

# 1) Secrets erzeugen
openssl rand -hex 64    # JWT_SECRET (min. 64)
openssl rand -hex 20    # DB_PASSWORD (min. 20)
openssl rand -hex 32    # WEBHOOK_SECRET_* (min. 32 je Quelle)

# 2) ENV-Datei anlegen und ausfüllen
cp deploy/.env.production.example deploy/.env.production
nano deploy/.env.production       # alle CHANGE_ME ersetzen

# 3) TLS-Zertifikat ablegen
mkdir -p /etc/ssl/soc
cp server.crt /etc/ssl/soc/server.crt
cp server.key /etc/ssl/soc/server.key
chmod 600 /etc/ssl/soc/server.key

# 4) Starten (baut api + web mit)
docker-compose -f deploy/docker-compose.prod.yml \
  --env-file deploy/.env.production up -d --build

Drei Container: soc_postgres_prod, soc_api_prod, soc_web_prod. Nur web ist von außen erreichbar (80/443).

6.3 nginx / TLS (deploy/nginx/nginx.conf)

  • HTTP → HTTPS-Redirect (301); TLS 1.2/1.3; HSTS + Security-Header.
  • /api/ → api:3000 (30s); /api/v1/integrations/ 60s; /api/v1/agent/ & /api/v1/use-case-drafts/ 600s (lokales LLM).
  • / → React-SPA (try_files … /index.html); /health → API-Health.
  • /metrics (Prometheus) → nur interne IPs (10.99.99.0/24, 127.0.0.1).
nginx steht für den KI-Agent auf 600s, App-Default ist niedriger (60s/120s). Bei langsamem CPU-Ollama OLLAMA_TIMEOUT_MS erhöhen, damit App- und nginx-Timeout zusammenpassen.

6.4 Release-Workflow (release.sh + soc.sh)

  1. HEAD merken, aktiven Branch ermitteln und git pull --ff-only origin <aktueller-branch>.
  2. Neue Commits anzeigen.
  3. soc.sh build api web (postgres braucht kein Build).
  4. soc.sh up (= up -d).
  5. 10s warten, soc.sh health (curl auf https://localhost/health).
  6. „RELEASE OK" oder Fehler + Exit-Code.
./deploy/release.sh

# soc.sh — Wrapper (setzt -f + --env-file automatisch)
./deploy/soc.sh ps
./deploy/soc.sh logs api
./deploy/soc.sh up
./deploy/soc.sh restart api
./deploy/soc.sh exec api npm run seed:admin
./deploy/soc.sh health
Veraltete Einzeiler wie ssh root@..., cd /apps oder git pull origin main sind absichtlich nicht mehr die Referenz. Wenn ./deploy/soc.sh nicht gefunden wird, befindest du dich nicht im geklonten Repo.

Backups (deploy/backup-db.sh)

  • pg_dump läuft im Container — DB-Creds verlassen ihn nie.
  • Pipeline pg_dump | gzip | openssl enc -aes-256-cbc -pbkdf2 → nie Klartext (DSGVO Art. 32).
  • Passphrase aus ~/.soc_backup_pass (0600). Integritätscheck + Rotation (Default: 14).
Passphrase getrennt sichern (Passwortmanager/Tresor) — geht sie verloren, sind alle Backups unwiederherstellbar.
./deploy/backup-db.sh
# Variablen: SOC_BACKUP_DIR (~/backups/soc), SOC_BACKUP_KEEP (14), SOC_BACKUP_PASS_FILE

# Restore:
openssl enc -d -aes-256-cbc -pbkdf2 -pass file:$HOME/.soc_backup_pass \
  -in soc-<TS>.sql.gz.enc | gunzip | \
  docker exec -i soc_postgres_prod sh -c 'psql -U "$POSTGRES_USER" "$POSTGRES_DB"'
