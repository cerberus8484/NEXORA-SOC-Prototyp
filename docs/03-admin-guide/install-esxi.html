Installations-Anleitung

VMware ESXi — SOC Ticket Tool auf VMware ESXi / vSphere VM deployen
Version 1.0  |  Stand: Juni 2026  |  Zielplattform: VMware ESXi 7.0+ / 8.0+

01 Voraussetzungen

Vor der Installation sicherstellen, dass die folgende Infrastruktur bereitsteht:

KomponenteMinimumEmpfohlen
VMware ESXi7.0+8.0+
vSphere ClientWeb-Client 7+vSphere 8
VM RAM4 GB8 GB
VM CPU2 vCPU4 vCPU
VM Disk50 GB SSD100 GB SSD
BetriebssystemUbuntu 22.04 LTSUbuntu 22.04 LTS
NetzwerkInternes VLANSOC-VLAN dediziert (dediziertes Portgroup)

Wichtig — ISO im Datastore: Das Ubuntu 22.04 LTS ISO muss vor der VM-Erstellung in einem ESXi-Datastore hochgeladen sein. vSphere Client → Storage → Datastore → Upload → ISO-Datei hochladen. Erst danach kann die VM erstellt werden.

02 VM erstellen (vSphere Client)

Die VM kann entweder über den vSphere Web Client oder per PowerCLI erstellt werden.

Via vSphere Web Client

  1. vSphere Web Client öffnen → Rechtsklick auf Host/Cluster → New Virtual Machine
  2. Select creation type: Create a new virtual machine
  3. Name & Location: Name: soc-ticket-tool, gewünschten Ordner wählen
  4. Compute Resource: ESXi-Host oder Cluster wählen
  5. Storage: Datastore mit mindestens 100 GB freiem Speicher wählen
  6. Compatibility: ESXi 7.0+ oder aktuell
  7. Guest OS: Linux → Ubuntu Linux (64-bit)
  8. Customize Hardware:
    • CPU: 4 vCPUs, Hardware Virtualization aktivieren
    • Memory: 8192 MB, Reserve all guest memory (für Produktion)
    • New Hard Disk: 100 GB, Thin Provision, SCSI-Controller
    • Network: VM Network oder dediziertes SOC-Portgroup, VMXNET3
    • CD/DVD Drive: Datastore ISO → Ubuntu 22.04 auswählen, Connect at Power On aktivieren
  9. Finish → VM einschalten → Console öffnen → Ubuntu installieren

Via PowerCLI (Alternative)

# PowerCLI (optional - für Automation)
Connect-VIServer -Server esxi.example.com
$vm = New-VM -Name "soc-ticket-tool" `
  -ResourcePool (Get-ResourcePool "Resources") `
  -Datastore (Get-Datastore "datastore1") `
  -NumCpu 4 -MemoryGB 8 `
  -GuestId ubuntu64Guest `
  -DiskGB 100 -DiskStorageFormat Thin
Netzwerk-Portgroup: Für SOC-Umgebungen empfiehlt sich ein dediziertes vSphere-Portgroup mit VLAN-Tagging, das ausschließlich SOC-relevante Hosts enthält. Das Portgroup unter vSphere → Networking → New Distributed Port Group anlegen.

03 Ubuntu 22.04 installieren

Die folgenden Schritte beziehen sich auf den Ubuntu Server Installer in der vSphere-Konsole:

  1. Language: English (empfohlen für konsistente Fehlermeldungen und Log-Auswertung)
  2. Network: DHCP oder statische IP konfigurieren — statische IP für Produktion empfohlen
  3. Storage: Gesamte Disk verwenden (guided), LVM-Gruppe bestätigen
  4. Profile: Username=socadmin, Hostname=soc-ticket, starkes Passwort vergeben
  5. OpenSSH Server: Aktivieren (Install OpenSSH server ankreuzen)
  6. Keine zusätzlichen Snaps installieren
  7. Nach Installation: Konsole → Login → IP-Adresse notieren (ip a)
Sicherheit: Nach der Installation sofort SSH-Zugang mit einem dedizierten SSH-Key absichern und Passwort-Login per SSH deaktivieren (PasswordAuthentication no in /etc/ssh/sshd_config).

04 VMware Tools installieren

Für optimale ESXi-Integration werden open-vm-tools installiert — der Open-Source-Ersatz für die proprietären VMware Tools:

# open-vm-tools für bessere ESXi-Integration
sudo apt install -y open-vm-tools
sudo systemctl enable --now open-vm-tools

# Prüfen
vmware-checkvm && echo "VMware Tools aktiv"

# Optional: für Desktop-VMs (nicht nötig für Server)
# sudo apt install -y open-vm-tools-desktop
Funktionen mit open-vm-tools:
  • VM-Snapshot aus ESXi ohne Datenverlust (konsistenter Snapshot)
  • Graceful Shutdown aus vSphere-Konsole
  • IP-Adresse in vSphere-Übersicht sichtbar
  • Memory Balloon Driver für dynamische Speicherverwaltung

05 System vorbereiten

Nach dem ersten Login als socadmin das System auf den aktuellen Stand bringen und Grundpakete installieren:

# System aktualisieren
sudo apt update && sudo apt upgrade -y

# Grundpakete
sudo apt install -y curl git wget htop ufw \
  ca-certificates gnupg lsb-release openssl

# Firewall konfigurieren
sudo ufw allow 22/tcp    # SSH
sudo ufw allow 80/tcp    # HTTP (Redirect)
sudo ufw allow 443/tcp   # HTTPS
sudo ufw enable
Hinweis: Im Gegensatz zur Proxmox-Installation entfällt hier der Qemu Guest Agent — stattdessen wurden in Abschnitt 04 die open-vm-tools installiert, die dieselbe Rolle für ESXi übernehmen.

06 Docker installieren

Docker wird über das offizielle Docker-Repository installiert — nicht über den Ubuntu-Standard-APT, da dieser veraltete Versionen liefert:

# Docker GPG Key
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | \
  sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

# Repository hinzufügen
echo "deb [arch=$(dpkg --print-architecture) \
  signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# Docker installieren
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin

# User zur Docker-Gruppe hinzufügen
sudo usermod -aG docker $USER
newgrp docker

# Test
docker --version
docker compose version
Sicherheit: Der docker-Gruppe angehörende User hat effektiv Root-Äquivalenz auf dem Host. In Produktionsumgebungen sollte der API-Prozess über einen dedizierten Service-Account ohne Shell-Login laufen.

07 Repository klonen

cd /opt
sudo mkdir soc-ticket && sudo chown $USER:$USER soc-ticket
cd soc-ticket
git clone https://github.com/cerberus8484/SOC-Orchestrator.git .
Deploy-Keys: Für automatische Updates (CI/CD) empfiehlt sich ein read-only Deploy-Key statt eines Personal Access Tokens. Diesen im GitHub-Repository unter Settings → Deploy Keys hinterlegen.

08 Konfiguration

TLS-Zertifikate ablegen und die Produktions-Umgebungsvariablen konfigurieren:

# TLS-Zertifikate ablegen
sudo mkdir -p /etc/ssl/soc

# Zertifikat von interner CA oder selbstsigniert (nur Dev):
sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/ssl/soc/server.key \
  -out /etc/ssl/soc/server.crt \
  -subj "/CN=soc.example.com"
sudo chmod 600 /etc/ssl/soc/server.key

# Produktions-ENV erstellen
cp deploy/.env.production.example deploy/.env.production

# Secrets generieren:
echo "JWT_SECRET=$(openssl rand -hex 64)"
echo "DB_PASSWORD=$(openssl rand -hex 20)"
echo "WEBHOOK_SECRET_GENERIC=$(openssl rand -hex 32)"

# Werte in deploy/.env.production eintragen:
nano deploy/.env.production
Wichtig: TLS_CERT_PATH und TLS_KEY_PATH in deploy/.env.production auf /etc/ssl/soc/server.crt und /etc/ssl/soc/server.key setzen.
Secrets: Die generierten Werte niemals in Git einchecken. Die Datei deploy/.env.production ist in .gitignore ausgeschlossen — trotzdem vor jedem Commit prüfen (git status).

09 Deployment starten

# Image bauen und starten
docker compose -f deploy/docker-compose.prod.yml \
  --env-file deploy/.env.production \
  up -d --build

# Status prüfen
docker compose -f deploy/docker-compose.prod.yml ps

# Migrationen ausführen
docker compose -f deploy/docker-compose.prod.yml \
  --env-file deploy/.env.production \
  exec api node -e "require('./src/db/pool').migrate().then(() => { console.log('Migration done'); process.exit(0); })"

# Logs verfolgen
docker compose -f deploy/docker-compose.prod.yml logs -f api
Erster Start: Beim ersten up --build werden alle Images gebaut und die Datenbank initialisiert. Dies kann 2–5 Minuten dauern. Die Migrationen erst ausführen, wenn alle Container den Status running zeigen.

10 Smoke Tests

Nach dem Start alle fünf Checks der Reihe nach ausführen. Alle Tests müssen erfolgreich sein, bevor die Installation als produktionsbereit gilt.

1. Healthcheck

curl -k https://soc.example.com/api/v1/health
# Erwartetes Ergebnis:
# {"status":"ok","db":"ok",...}

2. HTTPS-Redirect

curl -I http://soc.example.com/
# Erwartetes Ergebnis:
# HTTP/1.1 301 Moved Permanently
# Location: https://soc.example.com/

3. Unauthentifizierter Zugriff

curl -k https://soc.example.com/api/v1/tickets
# Erwartetes Ergebnis:
# HTTP 401 + {"error":"UNAUTHORIZED",...}

4. Login

curl -k -X POST https://soc.example.com/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@firma.de","password":"IhrPasswort"}'
# Erwartetes Ergebnis:
# {"token":"eyJ...","user":{...}}

5. Webhook-Test (mit korrektem HMAC)

TIMESTAMP=$(date +%s)
BODY='{"title":"Smoke Test Webhook","priority":"low"}'
SECRET="IhrWebhookSecret"
SIG="sha256=$(echo -n "${TIMESTAMP}.${BODY}" | openssl dgst -sha256 -hmac "$SECRET" | cut -d' ' -f2)"

curl -k -X POST https://soc.example.com/api/v1/integrations/generic/webhook \
  -H "Content-Type: application/json" \
  -H "X-Webhook-Signature: $SIG" \
  -H "X-Webhook-Timestamp: $TIMESTAMP" \
  -d "$BODY"
# Erwartetes Ergebnis:
# HTTP 202 + {"status":"accepted","eventId":"..."}
Checkliste vor Go-Live: JWT_SECRET gesetzt (min. 64 Zeichen) · DB_PASSWORD gesetzt (min. 20 Zeichen) · WEBHOOK_SECRET gesetzt für alle aktiven Quellen · CORS_ORIGINS nur interne Domain (kein * oder localhost) · TLS-Zertifikat gültig, Private Key nur root lesbar (chmod 600) · Kein externer Zugriff auf Port 3000 (Firewall)

11 Wartung & Updates

Update einspielen

cd <repo-root>
git pull --ff-only origin "$(git branch --show-current)"
docker compose -f deploy/docker-compose.prod.yml \
  --env-file deploy/.env.production \
  up -d --build api

Datenbank-Backup

docker compose -f deploy/docker-compose.prod.yml \
  --env-file deploy/.env.production \
  exec postgres pg_dump -U soc_api soc_tickets_prod > backup_$(date +%Y%m%d_%H%M%S).sql

vSphere-spezifische Hinweise

vSphere-Features für Produktionsbetrieb:
  • Snapshots: VM vor Updates snapshotten → bei Problemen innerhalb von Sekunden zurückrollen (vSphere → VM → Snapshots → Take Snapshot)
  • vSphere HA: Wenn HA aktiviert ist, startet die VM automatisch auf einem anderen Host neu bei Host-Ausfall — kein manueller Eingriff nötig
  • DRS: VM-Ressourcen werden automatisch auf Cluster-Hosts balanciert — sinnvoll bei schwankender Last
  • vSAN: Wenn verfügbar, für bessere I/O-Performance und Storage-Redundanz nutzen
  • Backup: VM-Level Backup via Veeam oder VMware Backup empfohlen — zusätzlich zu pg_dump, nicht als Ersatz
